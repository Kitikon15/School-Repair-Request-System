คำถามที่ 1.1

จงระบุ User Roles ทั้ง 3 ประเภท และอธิบายสิทธิ์การเข้าถึงข้อมูลของแต่ละบทบาท

  1. ผู้ดูแลระบบ (Admin): สิทธิ์เต็มในการจัดการระบบ สามารถจัดการข้อมูลผู้ใช้งาน (เพิ่ม/แก้ไข/ลบ/กำหนดบทบาท), มอบหมายงานแจ้งซ่อมให้ช่าง, ดู Dashboard สรุปภาพรวม และ export ข้อมูลรายงานทั้งหมด

  3. เจ้าหน้าที่ซ่อม / ช่าง (Technician): สิทธิ์ในการดูรายการงานซ่อมที่ได้รับมอบหมาย, อัปเดตสถานะงานซ่อม (รับเรื่อง -> กำลังดำเนินการ -> ซ่อมเสร็จ), แนบรูปภาพหลังการซ่อม และบันทึกผลการแก้ไขพร้อมค่าใช้จ่าย
คำถามที่ 1.2

จงสกัดคำนาม (Noun Extraction) จากโจทย์ความต้องการด้านบน เพื่อระบุคลาสที่ควรสร้างในระบบ (เช่น RepairRequest, User, Comment) และคำนามที่ไม่ควรสร้างเป็นคลาส พร้อมอธิบายเหตุผล

1. คำนามที่ควรสร้างเป็น คลาส (Domain Classes):

  • User: แทนผู้ใช้งานในระบบ (มีสิทธิ์ Admin, Teacher, Technician)
  • RepairRequest: แทนใบแจ้งซ่อม (เก็บบันทึกรายละเอียดปัญหา สถานะ และความเร่งด่วน)
  • RepairImage: แทนรูปภาพประกอบการซ่อม (รูปก่อน-หลังซ่อม)
  • Comment: แทนความคิดเห็นหรือการสอบถามเพิ่มเติมในใบแจ้งซ่อม

2. คำนามที่ไม่ควรสร้างเป็นคลาส พร้อมเหตุผล:

  • Building / Room: ไม่ควรสร้างเป็นคลาสแยกในระยะแรก แต่ควรเป็นเพียง Attributes (String) ใน `RepairRequest` เพื่อลดความซับซ้อน ยกเว้นกรณีต้องการบริหารจัดการพื้นที่ในระบบแยกต่างหาก
  • Urgency / ProblemType / Status: ควรเป็นเพียง Enum หรือ Attributes ของ `RepairRequest` ไม่ใช่คลาสอิสระ เพราะไม่มี พฤติกรรม (Behavior) ของตัวเอง
  • Dashboard / Report: ไม่ใช่ Domain Entity แต่เป็น View/Controller หรือบริการสำหรับแสดงผลสรุปข้อมูล

คำถามที่ 2.1

จงเขียน SQL CREATE TABLE สำหรับตาราง repair_requests พร้อมกำหนด Foreign Key Constraints และ CHECK Constraints ใน SQLite

CREATE TABLE repair_requests ( id INTEGER PRIMARY KEY AUTOINCREMENT, request_no TEXT UNIQUE NOT NULL, user_id INTEGER NOT NULL, building TEXT NOT NULL, room TEXT NOT NULL, problem_type TEXT NOT NULL CHECK(problem_type IN ('electrical', 'furniture', 'computer', 'aircon', 'other')), description TEXT NOT NULL, urgency TEXT NOT NULL DEFAULT 'medium' CHECK(urgency IN ('low', 'medium', 'high')), status TEXT NOT NULL DEFAULT 'pending' CHECK(status IN ('pending', 'accepted', 'in_progress', 'completed')), assigned_to INTEGER NULL, due_date DATE NULL, completion_date DATE NULL, cost REAL NULL, result TEXT NULL, created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE, FOREIGN KEY (assigned_to) REFERENCES users(id) ON DELETE SET NULL );
คำถามที่ 2.2

จงอธิบายความสัมพันธ์ (Relationships) ระหว่างตารางต่างๆ พร้อมระบุ Cardinality (1:1, 1:N, M:N) และอธิบายว่าเหตุใดจึงแยกตาราง repair_images ออกจาก repair_requests

ความสัมพันธ์ระหว่างตาราง (Cardinality):

  • users → repair_requests (1:N): ผู้ใช้ 1 คนสามารถแจ้งซ่อมได้หลายรายการ แต่ใบแจ้งซ่อม 1 ใบสร้างโดยผู้ใช้คนเดียว
  • users (ช่าง) → repair_requests (1:N): ช่าง 1 คนรับผิดชอบซ่อมได้หลายงาน แต่ใบแจ้งซ่อม 1 ใบถูกมอบหมายให้ช่างคนเดียว (`assigned_to`)
  • repair_requests → repair_images (1:N): ใบแจ้งซ่อม 1 ใบมีภาพแนบได้หลายภาพ (ทั้งก่อนซ่อมและหลังซ่อม)
  • repair_requests → comments (1:N): ใบแจ้งซ่อม 1 ใบมีหลายความคิดเห็น
  • users → comments (1:N): ผู้ใช้ 1 คนโพสต์ได้หลายความคิดเห็น

เหตุผลที่แยกตาราง `repair_images` ออกจาก `repair_requests`:

เป็นการปฏิบัติตามหลัก Database Normalization (1NF) เพื่อป้องกัน Repeating Groups เนื่องจากใบแจ้งซ่อม 1 ใบสามารถแนบรูปถ่ายได้มากกว่า 1 รูป (เช่น ก่อนซ่อม 2 รูป, หลังซ่อม 1 รูป) หากเก็บในตาราง `repair_requests` จะทำให้เกิดปัญหาต้องจอง column ไว้หลายช่อง (`img1`, `img2`) ซึ่งไม่ยืดหยุ่น การแยกตารางทำให้สามารถแนบกี่รูปก็ได้ และจัดการ metadata ของแต่ละรูปได้สะดวก

💻 ส่วนที่ 3: การพัฒนาด้วย Python 3.10+ (Python Implementation)

🔧 ตัวอย่างโค้ด: คลาส RepairRequest พร้อม Type Hints

from dataclasses import dataclass, field from datetime import date, datetime from typing import Optional from enum import Enum class RequestStatus(Enum): PENDING = "pending" ACCEPTED = "accepted" IN_PROGRESS = "in_progress" COMPLETED = "completed" class ProblemType(Enum): ELECTRICAL = "electrical" FURNITURE = "furniture" COMPUTER = "computer" AIRCON = "aircon" OTHER = "other" @dataclass class RepairRequest: """คลาสแทนใบแจ้งซ่อม (Repair Request)""" id: int request_no: str user_id: int building: str room: str problem_type: ProblemType description: str urgency: str = "medium" status: RequestStatus = RequestStatus.PENDING assigned_to: Optional[int] = None due_date: Optional[date] = None cost: Optional[float] = None created_at: datetime = field(default_factory=datetime.now) def assign_to(self, technician_id: int, due_date: date) -> None: """มอบหมายงานให้เจ้าหน้าที่""" self.assigned_to = technician_id self.due_date = due_date self.status = RequestStatus.ACCEPTED def start_repair(self) -> None: """เริ่มดำเนินการซ่อม (ต้องรับเรื่องก่อน)""" if self.status != RequestStatus.ACCEPTED: raise ValueError("Cannot start repair: Request not accepted yet") self.status = RequestStatus.IN_PROGRESS def complete_repair(self, cost: float, result: str) -> None: """บันทึกผลการซ่อม""" self.cost = cost self.status = RequestStatus.COMPLETED # Save result to database via repository # --- ตัวอย่างการใช้งาน --- request = RepairRequest( id=1, request_no="RP-202609-001", user_id=10, building="อาคาร 3", room="301", problem_type=ProblemType.AIRCON, description="แอร์ไม่เย็น มีเสียงดัง", urgency="high" ) request.assign_to(technician_id=5, due_date=date(2026, 9, 25)) request.start_repair() request.complete_repair(cost=1500.0, result="ล้างแอร์และเติมสารทำความเย็น") print(f"สถานะ: {request.status.value}, ค่าใช้จ่าย: {request.cost} บาท")
คำถามที่ 3.1

จากโค้ดข้างต้น จงอธิบายว่า:

  • หลักการ Encapsulation ถูกนำมาใช้อย่างไรใน Python (เปรียบเทียบกับ PHP)
  • เหตุใดจึงใช้ Optional[int] และ Optional[date] (Nullable Types)
  • @dataclass decorator ช่วยลดโค้ดซ้ำซ้อนอย่างไร
  • Encapsulation: ใช้การซ่อนสถานะภายในและการเปลี่ยนสถานะของวัตถุผ่าน Methods (เช่น `assign_to`, `start_repair`) เพื่อควบคุมความถูกต้องของข้อมูล แทนที่จะอนุญาตให้แก้ไข Attribute โดยตรง ใน Python จะใช้หลัก Convention เช่น การใช้ `_` สำหรับ Private Access ขณะที่ PHP ใช้ Keywords เช่น `private`/`protected` ในระดับ Language Level
  • การใช้ Optional[T]: เพื่อแสดงอย่างชัดเจนว่า Attribute นั้นมีสิทธิ์เป็น `None` (Null) ได้ เช่น `assigned_to` หรือ `due_date` จะยังไม่มีค่าจนกว่า Admin จะมอบหมายงาน ช่วยให้ Static Analysis Tools (เช่น mypy) ตรวจจับ Bug ประเภท `AttributeError` ได้ก่อนรันจริง
  • @dataclass Decorator: ช่วยสร้าง Method พื้นฐานให้อัตโนมัติ เช่น `__init__()`, `__repr__()`, `__eq__()` ทำให้ไม่ต้องเขียน Boilerplate Code ในการตั้งค่า `self.x = x` ซ้ำๆ เหมือนการเขียน Class ปกติ
คำถามที่ 3.2

จงเขียน Python Function สำหรับสร้างรหัสใบแจ้งซ่อมอัตโนมัติ (Format: RP-YYYYMM-XXX เช่น RP-202609-001) โดยใช้ datetime และ str.zfill()

from datetime import datetime def generate_request_no(sequence_number: int) -> str: """ สร้างรหัสใบแจ้งซ่อม รูปแบบ RP-YYYYMM-XXX :param sequence_number: ลำดับที่ของใบแจ้งซ่อมในเดือนนั้นๆ """ now = datetime.now() year_month = now.strftime("%Y%m") padded_seq = str(sequence_number).zfill(3) return f"RP-{year_month}-{padded_seq}" # ตัวอย่างทดสอบการใช้งาน print(generate_request_no(1)) # ผลลัพธ์: RP-202609-001 print(generate_request_no(45)) # ผลลัพธ์: RP-202609-045
คำถามที่ 3.3

จงอธิบาย State Transition ของ status ในคลาส RepairRequest ว่าเปลี่ยนจาก pending → accepted → in_progress → completed ได้อย่างไร และเหตุใดจึงต้องมีเงื่อนไขตรวจสอบใน method start_repair() (เปรียบเทียบกับหลักการ State Pattern)

State Transition & Validation:

การเปลี่ยนสถานะจาก pending → accepted → in_progress → completed ตามลำดับ ต้องผ่าน Business Rules ที่ถูกต้อง ใน method start_repair() มีการเช็คเงื่อนไข if self.status != RequestStatus.ACCEPTED: raise ValueError(...) เพื่อป้องกันการข้ามขั้นตอน เช่น งานที่ยังไม่มีการมอบหมายช่าง (`pending`) ไม่ควรถูกปรับเป็นกำลังดำเนินการ (`in_progress`) ได้ทันที

เปรียบเทียบกับ State Pattern:

แนวคิดนี้ประยุกต์มาจาก State Design Pattern เพื่อรับประกัน Data Integrity และความถูกต้องของกระบวนการทำงาน (Workflow) ซึ่งช่วยให้ระบบสามารถตรวจสอบสถานะปัจจุบันก่อนอนุญาตให้เกิด Action ถัดไป ป้องกันข้อผิดพลาดของข้อมูลในฐานข้อมูล

🔍 ข้อสงสัยที่พบบ่อย (Frequently Asked Questions)

รวมคำถามที่นักศึกษามักสงสัยในการวิเคราะห์และออกแบบระบบแจ้งซ่อมโรงเรียน (Python Edition) พร้อมแนวคำตอบเพื่อทบทวนความเข้าใจ

❓ Q1: ทำไมต้องใช้ Enum class สำหรับ RequestStatus และ ProblemType แทนการใช้ string ธรรมดา?
แนวคำตอบ: การใช้ Enum จาก module enum มีข้อดีหลายประการ:
  • Type Safety: ป้องกันการป้อนค่าผิด เช่น พิมพ์ "pendding" แทน "pending" → IDE จะเตือนทันที
  • Autocomplete: VS Code / PyCharm จะแนะนำค่าที่เป็นไปได้ทั้งหมด
  • Refactoring ง่าย: เปลี่ยนชื่อค่าจากที่เดียว ทุกจุดที่ใช้จะถูกอัปเดตอัตโนมัติ
  • Self-documenting: โค้ดอ่านเข้าใจได้เองว่าระบบมีสถานะอะไรบ้าง
  • SQLite CHECK: ใช้คู่กับ CHECK IN (...) ในฐานข้อมูลได้
❓ Q2: ทำไมต้องแยกตาราง repair_images ออกจาก repair_requests? เก็บเป็น path ในตารางหลักเลยไม่ได้หรือ?
แนวคำตอบ: การแยกตารางเป็นหลักการ Normalization (1NF) เพราะ:
  • 1 ใบแจ้งซ่อม มีหลายรูป: ความสัมพันธ์เป็น 1:N (อาจมีรูปก่อนซ่อม 2 รูป, หลังซ่อม 3 รูป)
  • ยืดหยุ่น: เพิ่มรูปได้ไม่จำกัด ไม่ต้องแก้โครงสร้างตาราง
  • Query ง่าย: SELECT * FROM repair_images WHERE repair_id = ?
  • ถ้าเก็บในตารางหลัก: ต้องสร้างคอลัมน์ image1, image2, image3... ซึ่งไม่ยืดหยุ่นและเสียพื้นที่
❓ Q3: ในโค้ด Python มี Optional[int] และ Optional[date] มันคืออะไร? ต่างจาก PHP ?int อย่างไร?
แนวคำตอบ: Optional[X] จาก module typing หมายความว่า ตัวแปรนั้นสามารถรับค่าเป็น type X หรือ ค่า None ก็ได้ (เทียบเท่า X | None ใน Python 3.10+)
  • PHP: ?int (Nullable Types) - ตรวจสอบตอน Runtime เท่านั้น
  • Python: Optional[int] - เป็น Type Hint สำหรับ Static Type Checker (mypy) และ IDE
  • มักใช้กับ Attribute ที่ "อาจจะยังไม่มีค่า" ในช่วงแรก เช่น assigned_to, due_date, cost
❓ Q4: @dataclass decorator คืออะไร? ทำไมต้องใช้?
แนวคำตอบ: @dataclass (Python 3.7+) เป็น decorator ที่สร้าง __init__, __repr__, __eq__ ให้อัตโนมัติจาก class attributes
  • ลด Boilerplate: ไม่ต้องเขียน __init__ เอง (เทียบเท่า Constructor Promotion ใน PHP 8)
  • อ่านง่าย: เห็นโครงสร้างข้อมูลได้ชัดเจนในบรรทัดเดียว
  • Immutable ได้: ใช้ @dataclass(frozen=True) สำหรับ immutable objects
  • เหมาะกับ Model: ใช้แทน ORM Model ในกรณีที่ไม่ต้องการความซับซ้อน
